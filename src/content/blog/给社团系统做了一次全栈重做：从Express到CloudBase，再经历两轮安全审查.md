接手这个系统时，它是一个 Express + SQL.js 的单文件后端（`server.js` 就有 33KB），加一个原生 JS 字符串拼 HTML 的前端。功能是齐的：战队、赛事、约战、活动、公告、管理后台全都有，UI 也下了功夫（电竞 HUD 风）。但用户看完只说了句：**"他做的我觉得不好，用你的 skill 充分修改，必要时可以重做。"**

于是就有了这篇文章：从选型、重做、上线，到被外部审查连续揪出 20 多个问题的完整过程。

## 为什么是全栈重做，而不是修补

动手前把 v1 完整读了一遍，问题清单很长，挑几条硬伤：

- **密码明文存储**，明文比对，注册页还明示"密码一经提交永久生效，无法修改"
- **token 永不过期**（sessions 表没有过期字段，不校验）
- **邀请码 = 队长学号后 6 位**，而且 `captain_sid` 在战队列表里全员可见——等于任何人都能算出邀请码加入任何战队
- 注册接口缺字段直接 500，排行榜排序有语义 bug，`routes/` 目录是空的、`activity.js` 是死代码

结论：修修补补不如重做。数据只有种子数据，重做零损失。

## 架构：BaaS 优先，业务全在云函数

技术栈定下来是 **Vue 3 + Vite + CloudBase（腾讯云开发）**，理由很简单：

1. **认证交给平台**——密码哈希、token 过期、修改密码全是平台能力，v1 的明文密码问题从根上消失
2. **数据库权限收紧**——14 个集合全部 ADMINONLY，客户端不直连，所有读写走云函数
3. **单云函数 + action 分发**——所有业务逻辑放一个 `cs2-api` 事件函数里，`event.action` 路由到对应处理函数。函数内自动有管理员权限和调用者身份（`auth.getUserInfo().uid`）

前端就是标准的 Vue 3：Router + Pinia，页面 8 个（登录、首页、战队、赛事、活动、通知、个人中心、管理后台），UI 按 Apple 风浅色手写（浅灰底、白卡片、毛玻璃、大圆角、`#0071e3` 苹果蓝）。

## 认证方案：平台不给直注册，就自己造 ticket

这是整个重做里最曲折的一块。

我的第一版设计是：前端 `auth.signUp({ username, password })` 创建平台用户 → 云函数落库。结果一跑，平台直接拒绝：**"you can not signup just by username and password"**——CloudBase 要求注册必须带邮箱/手机号验证，纯用户名密码注册只允许管理端创建。

解决方案是官方文档里的**自定义登录（custom login）**：注册时云函数校验表单 → `scrypt` 哈希密码存 `users` 集合 → 用私钥签发 ticket → 前端 `signInWithCustomTicket()` 登录，平台自动创建用户并管理会话。整个流程变成：

```
注册 → 云函数校验+哈希 → 返回 ticket → 前端 ticket 登录 → 平台建用户
登录 → 云函数校验哈希 → 签发 ticket → ticket 登录
```

这条路踩了三个坑：

1. **私钥字段名**：管理端生成的密钥 JSON 是 `privateKey` / `keyId`，但 node-sdk 实际读的是 `private_key` / `private_key_id`——少了 `env_id` 还直接报"当前私钥未包含 env_id 信息"
2. **自定义登录用户迁移**：注册时先用学号占位（`_id = 学号`），ticket 登录后第一次 `getMe` 再把文档迁移到平台 UID 下，否则用户管理里 sid/_id 会错位
3. **未登录调用云函数被拒**：匿名会话 2 小时过期后，`callFunction` 报 `INVALID_CREDENTIALS`——修复是在 API 层统一兜底：遇到这个错误自动重建匿名会话并重试一次，用户完全无感

## 上线后的第一次安全审查

系统上线、40 项全链路冒烟测试全绿之后，我把项目交给了外部安全审查（其实就是让模型/工具对着代码挑刺）。第一轮揪出的问题都挺实在：

| 优先级 | 问题 | 修复 |
| --- | --- | --- |
| P0 | 未激活账号可以绕过前端直接调云函数（`activated=0` 照样建队） | `requireActive()` 全量校验，19 处写操作统一拦截 |
| P0 | 用户列表接口返回 `password_hash` / `password_salt` | `sanitizeUser()` 统一脱敏 |
| P1 | 约战接受/拒绝能绕过管理员审核（状态机缺失） | 强制校验 `pending_accept` 状态 |
| P1 | 邀请码对所有游客公开 | 仅队长/成员可见 |
| P1 | 前端 `store.user?.uid` 拿到 `undefined` | getMe 统一返回 `uid` 字段 |

顺带还处理了 `.git/config` 里嵌入的 GitHub token——那是国内直连 GitHub 被墙时用 gh-proxy 推送留下的，等于把写权限亮在外面，必须吊销换凭据 helper。

## 第二轮：管理后台两个审核功能实际不可用

第一轮修完，审查者又来了，这次是功能级 bug，而且是**真·不可用**：

1. **战队审核按钮调用不存在的 API**——前端调 `api.approveTeam()`，但 `api.js` 里根本没这个函数。我把前端全部 66 个 `api.*` 调用和后端 action 清单交叉核对，就漏这俩
2. **管理员看不到入队申请**——`teamJoinRequests` 只允许队长调，管理员被挡在外面
3. **用户管理 sid/_id 混用**——管理端传学号，后端当文档主键用，一旦平台 UID ≠ 学号，激活/删除/级联全错
4. **密码无最大长度**——`scryptSync` 一个 10MB 的密码就能把云函数 CPU 打满

这轮的教训是：**冒烟测试只覆盖了"正确路径"，没覆盖"前端按钮到后端接口"这条链路**。测试直接调云函数 `adminTeamApprove`，永远发现不了 `api.js` 缺函数。

## 产品 bug：招募开了，怎么看不到？

上线后用户反馈："开启招募之后，招募中里没显示我的战队，bug 吗？"

查数据发现一个有意思的组合：

- 用户的「木叶暗部」是 **pending（待审核）** 状态——招募区只展示已通过审核的战队，所以它开了也不显示，而且前端还允许 pending 战队点"开启招募"（按钮存在但没效果）
- 用户的「Seventh Circle」是 approved 且招募已开启，但**招募中区的代码特意排除了自己的战队**（`!myIds.has(t.id)`），只显示别人的——自己开了招募想在招募区确认效果，看到"暂无"，当然以为没生效

修复两处：待审核战队不允许开招募（后端拦截 + 前端隐藏按钮）；招募中区显示所有招募中的战队，自己的标"我的战队"徽章。

## 复盘

1. **BaaS 选型对了一半**：认证、会话、存储交给平台确实省心，代价是平台绑定（体验版用户配额）和"平台不给你注册接口"这种设计约束——遇到约束先查官方文档，别硬试
2. **安全审查要持续做**：两轮 20+ 项修复里，"功能不可用"这类 bug 比安全漏洞更隐蔽。交叉核对（前端调用 ↔ 后端 action）比跑测试更有效
3. **冒烟测试别写死业务数据**：冠军墙被用户改过一次后，测试断言 `teamName === 'CS2 一队'` 就失败了——断言结构，不断言值
4. **产品规则要在后端定死**：一人一队、状态机流转、已毕业拦截这些规则，前端只是表现，后端校验才是防线

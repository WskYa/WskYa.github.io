先介绍一下这个系统：**CS2 电竞社团管理系统**，给学校电竞社团做的一套内部管理工具——战队、赛事、约战、活动、公告、管理后台，一个社团日常运营需要的东西都在里面。它已经上线运行，代码也开源了，这篇文章记录的是它从旧版本到全新重做的过程。

## 旧版本是什么样

我接手的时候，系统是 Express + SQL.js 写的，整个后端是一个 33KB 的 `server.js` 单文件，前端是原生 JS 字符串拼 HTML。功能倒是齐的，UI 也用心做了电竞 HUD 风格。但仔细看，问题不少：

- 密码是**明文存储**的，注册页甚至写着"密码一经提交永久生效，无法修改"
- 登录 token **永不过期**
- 邀请码就是队长学号的后 6 位，而队长学号在战队列表里人人可见
- 注册接口缺字段会直接 500

这些不是修修补补能解决的，而且当时的数据库里只有演示数据，重做没有迁移成本。所以决定：**全栈重做**。

## 新的技术方案

选型考虑了很久，最后定下来：

| 层 | 方案 | 原因 |
| --- | --- | --- |
| 前端 | Vue 3 + Vite | 组件化开发，页面多，需要一个正经框架 |
| 认证 | CloudBase 平台 Auth | 密码哈希、token 过期、修改密码全部平台负责 |
| 后端 | 单个云函数（action 分发） | 业务逻辑集中一处，函数内自带管理员权限和调用者身份 |
| 数据库 | CloudBase NoSQL，14 个集合 | 全部 ADMINONLY，客户端不直连，读写只走云函数 |
| UI | Apple 风浅色 | 浅灰底、白卡片、毛玻璃、大圆角，跟社团的硬核电竞风反着来，图个清爽 |

架构上是一条很清晰的数据流：

```
Vue 3 前端 → @cloudbase/js-sdk → app.callFunction() → cs2-api 云函数 → NoSQL 数据库
```

前端只管展示，所有业务逻辑（校验、状态流转、权限判断）都在云函数里，一个 `event.action` 路由到对应的处理函数。

## 认证：社团有自己的账号体系

这个系统要求用**学号**注册登录，但 CloudBase 平台的注册接口要求邮箱或手机号验证，不支持纯用户名密码注册。试了平台的 `signUp` 直接被拒，报错信息写得很直白：*"you can not signup just by username and password"*。

官方给的出路是**自定义登录（custom login）**：服务端用自己的私钥签发一个 ticket，客户端拿 ticket 登录，平台自动创建用户。于是注册登录变成了这样：

- **注册**：前端填表 → 云函数校验（学号格式、白名单、查重）→ 密码 scrypt 哈希存入 `users` 集合 → 签发 ticket → 前端 ticket 登录 → 平台建号
- **登录**：云函数校验密码哈希 → 签发新 ticket → ticket 登录

密码只以哈希形式存在，平台管会话，v1 的明文密码问题从根上消失了。

这中间有个小插曲：管理端生成的私钥 JSON 字段名是 `privateKey` / `keyId`，但 SDK 实际读的是 `private_key` / `private_key_id`，还要求必须带 `env_id` 且等于环境 ID。对着报错信息逐条试出来的，写在了项目的 README 里，避免后来的人再踩。

## 业务功能

功能上保留了 v1 的全部能力，重新梳理了一遍流程：

- **战队**：创建要管理员审核；邀请码是随机 6 位（不再跟学号挂钩）；一人只能属于一个战队；每队上限 12 人
- **约战**：完整的状态机——发起 → 管理员审核 → 对方队长确认 → 上报比分 → **对方确认后生效**（24 小时没确认自动生效），成绩才计入排名
- **赛事**：赛事管理、报名审核、对阵比分录入、排行榜（按胜场/胜率聚合）
- **活动**：发布、报名、名额限制、报名名单
- **通知中心**：入队结果、约战状态、比分确认这些都会推站内通知，侧边栏有未读红点
- **管理后台**：用户管理（搜索、分页、激活、角色、毕业、删除）、四类审核、注册白名单、公告、操作日志

## 上线与测试

系统部署后，我写了一个 40 项断言的**全链路冒烟测试**，用 Node 脚本模拟真实用户：注册 → 管理员激活 → 建队 → 审核 → 发起约战 → 接受 → 上报比分 → 对方确认 → 排名更新，一路走通，全绿。

## 两轮安全审查

上线之后，我把代码交给外部工具做安全审查。**第一轮**揪出的问题主要集中在"前端相信了不该信的"和"后端漏了该拦的"：

- 未激活的账号可以直接调云函数建队——`requireActive()` 统一校验，19 处写操作全部拦截
- 用户列表接口把密码哈希和盐一起返回了——加了一层 `sanitizeUser()` 脱敏
- 约战的接受/拒绝按钮能绕过管理员审核——状态机补上了前置校验
- 邀请码对所有游客可见——改成只有队长和队员能看到

**第二轮**的问题更隐蔽，是功能级的：

- 管理后台的"战队审核"按钮调用的 API 在 `api.js` 里根本不存在——前端 66 个 `api.*` 调用和后端 action 清单交叉核对，就漏了这两个
- 管理员在后台看不到入队申请——查看接口只允许队长调用，没放行管理员
- 用户管理用学号当数据库主键——统一改成用 `_id`
- 密码没有长度上限——一个超长密码就能让 scrypt 计算把云函数 CPU 打满，加了 72 字符上限

第二轮有个很典型的教训：冒烟测试直接调云函数接口，绕过了前端，所以"前端按钮 → API 封装 → 后端 action"这条链路断了，测试根本发现不了。

## 上线后的小插曲

用户反馈过一个挺有意思的问题："开启招募之后，招募中里没显示我的战队，bug 吗？"

查数据发现两个因素叠加：一个是待审核的战队本来就不会出现在招募区（招募区只展示已通过审核的战队），但前端却允许待审核战队点"开启招募"按钮；另一个是招募中区的代码**故意排除了自己的战队**，只显示别人的——所以自己开了招募想在招募区确认效果，看到"暂无"，当然觉得是 bug。

修复也简单：待审核战队不允许开招募；招募中区显示所有招募中的战队，自己的标一个"我的战队"徽章。

## 项目现在长什么样

系统已经稳定运行，代码开源在 [WskYa/esports-club-manager](https://github.com/WskYa/esports-club-manager)，做成了模板：环境变量注入配置、README 带完整部署指南、敏感信息零入库。给别的社团部署，按文档走 15 分钟能跑起来。
